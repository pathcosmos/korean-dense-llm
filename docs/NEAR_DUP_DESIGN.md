# 근접 중복(near-dup) 제거 설계안

상태: **설계안이며 구현·전수 실행은 하지 않았다.** 근거 수치는 `docs/DATA_VALUE_ASSESSMENT.md` 6절(표본 측정)과 아래에 표시한 이번 세션 실측뿐이다. 확인하지 못한 항목은 "미확인"으로 적었다.

## 1. 왜 필요한가 (측정된 것과 아닌 것)

| 항목 | 값 | 출처·신뢰도 |
|---|---|---|
| 소스 내·소스 간 exact 중복 | 0건 | 전수 검증 (6절 1) |
| HPLT 문서 중 FineWeb2에 J≥0.8 쌍이 있는 비율 | 약 23% (구간 18~29%) | 표본 추정 (6절 2) |
| 같은 비율, J≥0.5 | 약 42% | 표본 추정, 변형·부분 겹침 포함 |
| 같은 소스 안의 근접 중복 | 연속 15k 문서 구간에서 0~0.007% | 국소 측정, **전체 소스 값 아님** |
| FineWeb2 ↔ FineWeb-Edu 등 다른 소스와의 중복 | 미측정 | |
| 학습 split과 eval split 사이의 근접 중복 | 미측정 | 아래 5절 |

HPLT 쪽 중복을 거친 곱셈(23% × 28.77B)으로 환산하면 약 6.6B 토큰(한국어 웹의 약 9%)이다. 문서 길이 편향을 반영하지 않은 값이다.

## 2. JUN이 정해야 하는 정책 (제 권고 포함)

| 결정 | 선택지 | 권고와 이유 |
|---|---|---|
| 적용 범위 | (a) FW2↔HPLT 교차만 (b) 한국어 전 소스 교차+소스 내 (c) 영어·수학·코드 포함 | (b). 측정된 문제는 교차 중복이지만 소스 내 전체 값이 미측정이라, 먼저 측정 단계(6절 1단계)를 거쳐 범위를 확정한다 |
| 임계값 J | 0.8 / 0.7 / 0.5 | 0.8. 어절 2~3% 이내 차이만 같은 글로 본다. 0.5는 같은 글의 변형까지 지우므로 학습 이득에 대한 근거 없이는 쓰지 않는다 |
| 생존 문서 규칙 | (a) 소스 우선순위(wiki > FW2 > HPLT) (b) 클러스터 내 가장 긴 문서 (c) 임의 | 소스 우선순위로 정한 뒤 같은 소스끼리는 (b). 기존 `data/dedup.py`가 소스 순서로 생존자를 정하므로 계약과 일관된다. 단 "긴 문서가 보일러플레이트가 더 많은 쪽일 수 있다"는 약점이 있다 |
| 적용 대상 | (a) 새 release 만 (b) 현 v1.0.1 bin 사후 보정 | 5절의 제약 때문에 (b)는 별도 단계가 필요하다 |

## 3. 검출기 사양

6절에서 검증한 구성을 그대로 쓴다.

- 정규화: NFKC → 소문자. 공백 분리 어절 **5-gram shingle**, 문서당 최대 5,000어절.
- 서명: 128 permutation MinHash (uint32). 300자 미만·5어절 미만 문서는 대상에서 제외.
- 후보: 32 band × 4 row LSH. 후보 쌍은 128개 서명 일치율로 J를 추정하고 임계값 이상만 중복으로 확정.
- 후보 포착 확률 `1-(1-J^4)^32` (계산값): J=0.3 → 0.229, 0.5 → 0.873, 0.6 → 0.988, 0.7 → 0.9998, 0.8 이상 → 1.0. 즉 J≥0.7에서는 사실상 빠짐이 없고, J=0.5 쌍은 약 13%가 후보에서 누락된다. 임계값이 0.8이면 이 누락은 문제가 되지 않는다.
- 검증 이력: 어절 0/2/5/10/30% 변경에서 추정 J 1.00/0.83/0.63/0.41/0.10, 무관 문서 0.00 (6절).
- 클러스터링: 확정된 쌍으로 connected components. 사슬(A~B, B~C, A≁C)로 큰 군집이 생길 수 있으므로 **군집 크기 분포와 최대 군집 몇 개를 반드시 읽어 본다.** 필요하면 군집 안에서 생존자와의 J를 다시 확인해 임계값 미만인 문서는 되살린다(미구현).

## 4. 비용 추정 (실측 기반, 하한)

- 이 샌드박스에서 FineWeb2 표본 400문서(평균 1,558자)의 서명 계산은 **문서당 약 3,000개/초·코어**(4.7M자/초)였다. 샌드박스는 4코어·RAM 15GB이다.
- 이 속도로 한국어 86.1M 문서(FW2 58.66M + HPLT 27.43M)는 약 **8 코어-시간**이다. 평균 길이가 더 긴 문서와 어절 상한 5,000 근처의 문서에서는 더 오래 걸리므로 하한으로 읽는다. 위키·영어·코드는 포함하지 않았다.
- 저장: 서명 전체는 128×4B = 512B/문서 → 86.1M 문서 약 **44GB**. band 키(32×8B)만 두면 약 22GB. 이 샌드박스의 여유 디스크는 15GB라 **전수 처리는 여기서 할 수 없다.**
- LSH는 band별 외부 정렬(또는 해시 파티션)로 그룹을 만든다. 메모리에 올릴 필요는 없다.
- 위 수치는 CPU 계산량의 추정이다. HF에서 원본 parquet를 전부 읽는 I/O와 네트워크 시간은 포함하지 않았다.

## 5. 기존 파이프라인과의 접점

### 5.1 token bin은 문서 단위로 제외할 수 없다

`train/data.py`의 `MixSampler`는 소스를 가중치로 뽑고 shard 안에서 **무작위 offset의 연속 구간**을 읽는다. 문서 경계나 문서 마스크를 쓰지 않는다. 따라서 중복 문서를 빼려면 샘플러 수준이 아니라 **bin 자체를 다시 만들어야 한다.**

- 방법 A: 중복 제거 후의 clean parquet로 `tokenize_shards.py`를 다시 돌린다 (재토큰화, 비용 큼).
- 방법 B: 문서 offsets(`data/release_offsets.py`가 EOS로 복구)를 이용해 유지할 문서의 토큰 구간만 복사해 bin을 압축한다. 재토큰화가 필요 없어 비용이 작지만 **offsets가 모든 소스에 대해 존재하는지, EOS 복구가 압축 후에도 같은 문서 수를 내는지는 확인하지 못했다.**
- 두 방법 모두 `SAMPLER_VERSION`/mix 계약의 입력이 바뀌므로 contract id가 달라진다. 이미 진행 중인 3B 학습의 resume에는 쓸 수 없다(resume은 입력 계약 일치를 요구).

### 5.2 학습량에 미치는 영향 (거친 계산)

계획 학습량 119.54B 토큰 중 HPLT 몫은 20% = 23.9B이다. HPLT 28.77B에서 약 6.6B가 빠지면(23% 가정) 22.2B가 남아 **유효 epoch이 0.83 → 약 1.08**로 오른다. 반대로 FW2가 중복의 생존자이면 FW2 쪽은 줄지 않는다. 생존자를 HPLT로 하면 FW2에서 약 11%(6절의 일대일 가정 환산)가 빠져 42.31B → 약 37.7B, 필요량 35.3B 대비 약 0.94 epoch이다. 둘 다 이론상 같은 학습량을 유지할 수 있는 수준이지만, 위 비율은 표본 추정과 길이 편향 무시에 의존한 값이다.

### 5.3 train/eval 분리

`data/split_manifest.py`의 분리는 동일 본문, 웹 NFC 동등 본문, 코드 저장소 연결 그룹만 같은 쪽으로 보낸다(코드 주석에도 "near-duplicate policy remain separate"). 근접 중복 쌍이 train과 eval에 갈라져 있으면 eval perplexity가 낙관적으로 나온다. 이 크기는 **미측정**이므로 1단계에서 eval 문서를 인덱싱해 train 전체와 대조한다. 중복 제거를 적용하게 되면 클러스터 ID를 split의 그룹 키로 추가해 같은 쪽으로 보내야 한다(현 v1.0.1 split은 바꾸면 held-out이 달라지므로 새 release 에서만 가능).

### 5.4 계약·산출물

- 새 단계 `data/neardup.py`(미작성)는 텍스트를 다시 쓰지 않고 **제거 목록**을 만든다: `(source, shard, row, content_sha256, cluster_id, kept, survivor_id, j)`. 원본 clean 트리는 `data/dedup.py`처럼 건드리지 않는다.
- 정책 문자열은 `minhash-w5-p128-b32r4-j0.80-v1` 같은 형태로 manifest에 고정하고, 입력 파일 크기·mtime·순서 서명을 포함한다(`data/dedup.py`의 방식을 따름).
- `data/quality_report.py`의 `near_duplicate_policy` 결정에는 "이유·범위·행동과 내용 hash로 고정한 증거"가 필요하다(`docs/DATA_CONTRACT.md`). 위 제거 목록과 검증 보고서의 hash가 그 증거가 된다. 이를 "전체 무중복 증명"으로 표시하면 안 된다.

## 6. 단계와 합격 기준 (실행 시간은 추정하지 않음)

1. **측정**: (a) 소스 내부 근접 중복 비율, (b) FW2↔FineWeb-Edu 등 나머지 쌍, (c) train↔eval 근접 중복. 합격 기준은 없다. 이 결과로 2절의 범위를 확정한다.
2. **전수 서명 생성**: 소스·shard별 서명 파일(재개 가능, `.done` 마커). 서명 입력의 정규화 규칙은 코드 해시로 고정한다.
3. **후보·검증**: band 정렬 → 후보 쌍 → 128서명 J 확인.
4. **정밀도 검사**: J 구간 [0.5,0.65) [0.65,0.8) [0.8,0.9) [0.9,1.0]에서 각 100쌍을 무작위로 읽어 "같은 글인가"를 판정한다. 이 판정은 품질 판단이 아니라 동일성 판단이라 모델도 쓸 수 있으나 판정 결과는 공개하고, 임계값 0.8 구간의 오탐이 높으면(기준 미정, 사전에 JUN이 정할 것) 임계값을 올린다.
5. **재현율 검사**: 실제 문서에 어절 단위 변형(0~30%)과 머리글·꼬리말 추가를 합성해 주입하고 회수율을 본다. 6절의 검증은 어절 치환만 다뤘고 **머리글·꼬리말 추가에 대한 J 하락은 측정하지 않았다**(6절 쌍 분석에서 같은 글의 차이가 주로 주변 텍스트였음을 고려하면 중요).
6. **군집 점검**: 크기 분포, 최대 군집 상위 20개를 읽는다. 대형 군집이 보일러플레이트(약관, 면책 공고 등)로 이뤄졌다면 문서 중복이 아니라 **줄·문단 단위 중복**이므로 아래 7절로 간다.
7. **제거 목록 확정 → bin 압축/재토큰화(5.1) → 새 release와 토큰 수 보고**.

## 7. 이 설계가 놓치는 것

- **문서 단위 J는 본문이 같고 주변 텍스트가 크게 다른 쌍을 놓칠 수 있다.** 본문이 짧고 보일러플레이트가 긴 문서에서 특히 그렇다. 보완책은 줄·문단 해시 기반 반복 제거(CCNet류의 문단 단위 dedup)나 접미사 배열 기반 부분문자열 dedup(Lee et al., 2022, "Deduplicating Training Data Makes Language Models Better")이다. 둘 다 이 코퍼스에서 효과를 측정하지 않았다. 문단 단위 방법은 제거 후 문서가 문맥을 잃는 부작용이 있다(일반적으로 알려진 trade-off이며 이 코퍼스에서 확인하지는 않았다).
- **중복이 학습에 해로운 정도는 측정하지 못했다.** 공개 문헌에서 중복 제거가 기억·perplexity에 이득이라는 보고가 있으나, 3B 규모와 한국어 웹에서의 이득 크기는 이 저장소의 근거가 아니다. 이를 확인하려면 소형 모델 ablation(GPU 필요, 미실행)이 필요하다.
- **저품질 문서는 지우지 않는다.** 근접 중복 제거는 품질 필터가 아니다(`DATA_VALUE_ASSESSMENT.md` 5.1, 14절).
- 영어(FineWeb-Edu)·수학(OWM)·코드는 이 설계의 측정 범위 밖이다. 코드는 `clean_code.py`가 저장소 그룹을 이미 다룬다.
- 세션에서 쓴 측정 스크립트는 저장소에 포함하지 않았다. 구현 시 `data/neardup.py`로 새로 작성해 단위 테스트(합성 변형 회수율)와 함께 넣어야 한다.

## 8. 결정이 필요한 것 (JUN)

1. 2절 표의 네 가지 정책 결정.
2. 6절 4단계의 오탐 허용 기준 (예: J∈[0.8,0.9) 100쌍 중 "다른 글" 몇 건까지).
3. 새 release를 만들 의사가 있는지. 현 v1.0.1과 진행 중인 학습에는 적용할 수 없다.
