# HF 연결 데이터의 한국어 LLM 학습 자료 가치 평가

평가일 2026-11-09. 대상: `pathcosmos/korean-pretrain-corpus`(태그 v1.1.1)와 `pathcosmos/korean-pretrain-training-data`(태그 v1.0.1). 관점 가중치는 **공개 한국어 코퍼스로서의 가치 60% / 3B 사전학습 입력으로서의 적합성 40%**.

> 방법과 한계. 수치는 두 종류다. (A) 저장소·HF가 공표한 값을 직접 대조한 것, (B) 이번에 소스별 무작위 샘플(한국어 3개 소스 각 약 1,500문서, 영어·수학 각 600문서)로 측정한 것. (B)는 95% 신뢰구간이 대략 ±2.5%p이고, 키워드·정규식 기반이라 거친 지표다. 문서 단위 사람 라벨링은 하지 않았다. 샘플은 소스당 5개 shard에서 추출했으므로 shard 간 편차는 반영하지 못한다.

- 토큰은 uint16 bin 242.4GB ÷ 2이며 manifest의 `train_tokens`(121,174,609,758)와 일치한다.

- FineWeb2 `kor_Hang/train`(25 파일)과 HPLT2.0 `kor_Hang`(464 파일)은 **업스트림 파일 수와 동일**하다. 이 두 소스에서는 더 가져올 한국어 웹이 남아 있지 않다. FineWeb-Edu는 140개 중 56개 shard만 사용했다.
- 한국어 순수 토큰 약 71B은 3B 모델에는 충분하지만(토큰/파라미터 비 약 24), 더 큰 모델이나 여러 epoch에는 부족하다.

## 2. 강점

1. **추적성·재현성이 이례적으로 높다.** 업스트림 revision 고정, 파일별 SHA256(`CHECKSUMS.json`), 문서별 split 배정·token offset·provenance parquet, 원본 정제 parquet bytes 보존, anonymous reader. 이번에 태그·manifest·tokenizer 다운로드, 3.9GB bin의 range 요청까지 실제로 동작을 확인했다.
2. **train/eval 분리가 구조적으로 설계됐다.** 동일 본문·NFC 동등 본문·코드 저장소 연결 그룹을 같은 쪽으로 보낸다. 공개 corpus 샘플 32건씩의 분리 검증이 기록돼 있고 token bin은 이미 train/validation이 분리돼 있다.
3. **토크나이저가 한국어에 효율적이다 (B).** 같은 한국어 샘플에서 어절당 토큰 수는 이 토크나이저 2.0–2.4, polyglot-ko(30k) 2.4–2.6, Qwen2.5(152k) 3.1–3.4. 영어는 1.40 vs Qwen 1.32로 근소하게 불리하다. 단 토크나이저가 이 코퍼스로 학습됐으므로 다른 도메인에서는 이득이 줄 수 있다.
4. **코드 데이터의 라이선스 라벨이 permissive 일색이다 (A).** 2,148,459 파일 전부 MIT 43.1%, Apache-2.0 40.1%, BSD-3 10.2%, CC0 2.6%, BSD-2 2.5%, Unlicense 1.0%, ISC 0.6%. GPL 계열 0%.
5. **exact 중복은 전수 검증으로 0건이다 (A, 6절).** FineWeb2 58,664,414건 + HPLT 27,434,232건의 `content_sha256` 전수를 대조해 소스 내·소스 간 exact 중복이 모두 0건임을 확인했다. 또 같은 소스 안의 연속 15k 문서 구간에서는 근접 중복도 0–0.007%였다. **그러나 소스 간 근접 중복은 높다 — 3.2절 참조.**
6. **파이프라인이 실제로 돈다.** CPU 환경에서 `quickstart_cpu.py`가 통과하고 테스트 258 통과/35 건너뜀으로 README 수치와 일치한다.
7. **개인정보 마스킹이 하이픈형 번호·이메일에는 작동한다 (B).** 샘플에서 이메일 0%, 하이픈형 전화번호 0%, 주민번호형 0%.
8. **지식·추론형 한국어 benchmark와의 문자열 겹침이 거의 없다 (B, 9절).** KMMLU(평가 가능 29,972문항 중 9건, 0.03%), HAE-RAE(4,877문항 중 0건), HRM8K(0건), KorMedMCQA(1,435문항 중 0건)에서 80% 이상 겹치는 문항이 스캔 범위 안에 거의 없었다.
9. **비한국어 50%(영어·수학·코드)는 한국어 웹보다 깨끗하다 (B, 10절).** 표본에서 보일러플레이트·스팸·이메일이 거의 없고, 코드는 exact 중복 0건에 permissive 라이선스 라벨뿐이다.

## 3. 부족한 점

### 3.1 데이터 품질

- **Wikipedia 정제 결함 (A, 전수 455,397건, 8절).** 31.7%에 빈 괄호 흔적(`()` 19.0%, `(,` 14.6%; 템플릿 제거 잔재, 예: "제임스 얼 카터 주니어(, 1924년 10월 1일~)"). 문서 끝 4줄 안에 말뭉치 전체에서 1,000문서 이상 반복되는 짧은 줄(카테고리·섹션 제목류)이 있는 문서가 44.0%(200문서 이상 기준 61.7%, 50문서 이상 기준 81.4%). 중앙 길이 572자, 300자 미만 18.8%, 500자 미만 43.9%(추정 토큰 비중 11.8%). `<ref`·`{{`·`[[`·HTML 등 마크업 잔재는 각 0.5% 미만. 가중치는 0.5%지만 약 2 epoch 반복된다. 앞선 표본 지표(카테고리 줄 18.4%)는 표본 내 반복만 세어 과소추정이었다.
- **웹 소스의 상용·내비게이션 보일러플레이트 (B).** FineWeb2 문서의 26%, HPLT 19%가 로그인·저작권·댓글 등 내비게이션 키워드를 포함한다(거친 지표). 샘플 내 동일 줄이 5회 이상 반복되는 문서가 FineWeb2 7.5%, HPLT 11.6%. HPLT 샘플의 한 쇼핑·자료 사이트 문구가 1,500건 중 69건(4.6%)에 반복됐다.
- **스팸·SEO 삽입이 정규식 추정보다 훨씬 많다 (B, 11절).** 정규식(도박어 2개 이상)은 FineWeb2 2.7%, HPLT 1.7%만 잡았지만, 문서를 직접 읽은 두 모델 라벨러는 웹 무작위 표본 80건 중 **9건(11%, 95% 구간 약 6~20%)** 을 스팸·SEO로 판정했고 두 라벨러의 건수가 같았다. 대부분 시험 덤프 광고 문구 사이에 소설·뉴스 문장을 끼워 넣은 형태(IT 자격증 덤프, 카지노·출장마사지 키워드 삽입)라 도박어 정규식으로는 걸리지 않는다. 키워드 삽입 문서 필터가 따로 필요하다.
- **개인정보 마스킹이 불완전하다 (B).** 점(.)으로 구분된 전화번호(`010.xxxx.xxxx`, `02.xxxx.xxxx`)가 FineWeb2·HPLT 샘플에서 각각 소수 건 발견됐다(한 문서에서 같은 번호가 6회). README도 "일부 패턴"만 마스킹한다고 명시한다.
- **레지스터 편중 (B).** 합쇼체(-습니다) 문서 약 54%, 평어(-다) 60–65%, 해요체 15–19%. 뉴스성 문서 25–30%, 상거래성 16–21%. 대화체·구어체·질의응답·논문·법률 문서는 의도된 구성이 아니다. 지시 이행(SFT) 데이터는 포함돼 있지 않다.

### 3.2 구성·규모

- 한국어 순수 웹은 업스트림에서 소진됐다. 확장하려면 새 소스가 필요하다.
- Wikipedia 덤프가 2023-11-01이고 약 0.29B 토큰에 불과해 지식 밀도 높은 소스가 얇다.
- 영어 FineWeb-Edu가 mix의 30%를 차지한다. 한국어 모델을 목표로 한다면 비중이 과한지 근거 실험이 필요하다(아래 4절). 코드는 약 3 epoch 반복된다.
- **FineWeb2↔HPLT 소스 간 근접 중복이 크다 (B, 6절).** 같은 글이 추출 방식 차이(머리글·꼬리말·메뉴·공백)만 다른 채 양쪽에 들어 있다. exact 해시(공백·대소문자 보존 NFC SHA256)는 이를 구조적으로 잡지 못한다. 층화 표본 측정으로 **HPLT 문서의 약 23%(95% 구간 약 18~29%)가 FineWeb2에 사실상 같은 글(J≥0.8)을 갖는 것으로 추정**되며, 어절 약 8% 변경까지 넓히면(J≥0.5) 약 42%다. 거친 토큰 환산으로 한국어 웹 71.4B 중 약 6.6B(약 9%)가 중복 노출일 수 있다. mix에서 FineWeb2 29.5% + HPLT 20.0%로 둘을 합쳐 쓰므로 실효 다양성이 그만큼 낮아진다.

### 3.3 라이선스·권리 (공개 코퍼스 관점에서 가장 큰 위험)

- pathcosmos 8개 repo 모두 HF 라이선스 필드가 `other`다. 원문 권리를 해소하지 않으며, 소스별 LICENSE-SCOPE에서 사용자가 직접 확인하도록 한다.
- Wikipedia: LICENSE-SCOPE가 "HF 카드 라벨이 Wikimedia의 2023 CC BY-SA 4.0 전환과 다름, 문서별 귀속·예외 확인 필요"라고 명시한다. 문서별 저자 귀속 정보가 데이터에 포함돼 있는지는 확인하지 못했다.
- FineWeb2·FineWeb-Edu·OpenWebMath는 ODC-By + Common Crawl 이용약관, HPLT는 CC0가 "packaging"에만 적용되고 원문 소유권은 주장하지 않는다. 웹 텍스트 개별 저작권은 해소되지 않는다.
- 코드: 라벨은 permissive지만 530,331개 저장소 **전부** `original_git_commit_verified=false`, `license_notice_bundle_verified=false`다. 즉 라이선스 라벨은 메타데이터일 뿐 NOTICE·귀속 의무 이행은 검증되지 않았다.
- 프로젝트 문서 자체가 "모든 원문에 대한 무조건적 상업 재배포 허가를 주장하지 않는다"고 선언한다.

### 3.4 검증 체계

- 평가 harness(`eval/`: ko/en perplexity, 로컬 선택형 task, 생성)는 있으나 **한국어 benchmark task가 하나도 포함돼 있지 않다.** 모델 가중치도 없고 본학습은 공개 시점에 진행 중이었다. 따라서 데이터가 실제로 좋은 모델을 만든다는 경험적 증거가 없다.
- 전체 3B 독립 재현은 검증되지 않았다(문서에 명시).

- **독해형 benchmark의 지문이 코퍼스에 대량으로 들어 있다 (B, 9절).** KorQuAD 지문의 87.0%(835/960), KLUE-MRC 지문의 29.1%(1,544/5,309), KoBEST-BoolQ의 28.7%(402/1,403)가 80% 이상 겹친다(Wikipedia 전수 스캔만으로 각각 80.3%, 26.8%, 25.9%). 지문이 위키·뉴스 본문이라 자연스러운 현상이지만, 이 데이터로 학습한 모델의 해당 benchmark 점수는 지문을 이미 본 상태의 값이다. 질문·정답 자체의 누출은 문항이 짧아 이 방법으로는 판정할 수 없었다.
- **코드 데이터가 소수 언어·소수 저장소에 치우쳐 있다 (A, 10절).** Java 32.9%, JavaScript 22.6%, Python 11.5%가 합쳐 약 67%이고, 단일 저장소 한 곳(`lfreneda/cepdb`)이 49,879파일(2.3%)을 차지한다. 코드는 mix에서 10%지만 4.0B 토큰을 약 3 epoch 반복한다.

## 4. 보강안

우선순위는 공개 코퍼스 가치(60%)에 직결되는 것부터.

1. **권리 정보 강화 (최우선).** 웹 문서에 도메인·URL 해시 수준의 출처 메타데이터와 opt-out/takedown 절차, Wikipedia 문서별 귀속 목록, 코드 저장소별 LICENSE·NOTICE 번들. 이것이 없으면 상업적 활용 판단이 불가능하다.
2. **재현 가능한 품질 필터 추가 및 리포트 공개.** (a) 줄 단위 템플릿 중복 제거(다문서 반복 줄), (b) 도박·SEO 삽입 분류기, (c) 한국어 교육성 분류기(FineWeb-Edu 방식), (d) 점·공백 변형 전화번호 등 마스킹 패턴 확장. 각 필터의 제거율을 샘플과 함께 공개.
3. **Wikipedia 재정제.** 카테고리 줄·빈 괄호 제거, 최신 덤프로 교체, stub 임계 적용.
4. **소스 간 근접 중복 제거 (측정은 6절에서 완료, 전수 처리는 미완).** 추정 비율이 큰 만큼 전수 MinHash-LSH(소스 간)로 정확한 쌍 목록을 만들고 한쪽만 남기는 v2 dedup을 적용한 뒤, 제거율과 토큰 수 변화를 공개. exact 해시 대신 공백·메뉴 변형에 강한 근접 중복 기준이 필요하다. 원본 URL이 데이터에 없어 URL 기반 겹침은 쓸 수 없다. 저장소의 `probe_similarity_recall.py`를 확장할 수 있다.
5. **한국어 benchmark 연결과 decontamination.** 접근 가능성은 9절에서 확인했다(KMMLU, HAE-RAE Bench 1.1, KoBEST, KLUE, KorMedMCQA, KorQuAD 1.0, HRM8K 모두 공개·비gated). `eval/multiple_choice.py`의 task 형식으로 변환하고, 학습 입력에서 겹치는 문서(특히 KMMLU 문항이 실린 시험 문제 모음 페이지)를 제거하거나 독해형 benchmark의 지문 노출을 표기한다. 어절 8-gram 정확 일치만 본 이번 검사는 번역·패러프레이즈를 잡지 못한다.
6. **mix 근거 실험.** 100M급 소형 모델로 한국어 50% vs 더 높은 비중, 영어 edu 30% vs 15% 등을 비교한 ablation 결과를 공개. 현재 가중치의 근거는 문서에 없다.
7. **도메인·레지스터 확장.** 뉴스 외 법률·특허·학술·공공문서, 대화체, 한영 병렬. 구체 후보의 라이선스는 소스별로 확인해야 하며 이번에는 검토하지 않았다.
8. **지시 이행·대화 데이터 분리 배포.** 사전학습 코퍼스와 별도 라이선스 설명으로.

| 공개 코퍼스: 품질·정제 | 60% 중 약 1/3 | 중 (위키 정제 결함, 웹 보일러플레이트·스팸 잔존). 단 **문서 단위 품질 비율은 측정하지 못했다**(아래 5.1) |

| 3B 사전학습: 검증 가능성 | 40% 중 절반 | 하 (한국어 benchmark 없음, 본학습 결과 미공개) |

### 5.1 품질 축의 근거와 한계 (13절 반영)

모델 라벨러(Claude, 서브에이전트)의 사용 가능/제외 판정은 JUN의 판정을 재현하지 못했다(JUN과의 kappa: 정답 30건 0.25~0.38, 새 검증 20건 가중 0.28~0.35, 기준 0.6 미달). 기준을 v2에서 v3로 고쳐도 올라가지 않았다. 이에 따라 다음과 같이 정리한다.

- **"웹 문서의 N%가 사용 가능"이라는 문서 단위 품질 비율은 이 보고서의 측정값으로 인정하지 않는다.** 11절의 65~80%, 13절의 모델 기준 77~86%는 모델 라벨러의 값이며 JUN 판단과 일치하지 않는다. JUN의 판정 50건(정답 30 + 검증 20)에서 읽은 약 79~80%는 표본이 작아 오차가 ±20%p 이상이므로 "대략 4분의 3에서 5분의 4 사이로 보이나 불확실"로만 쓴다.
- **품질 축의 근거로 남기는 것은 단순·검증 가능한 지표뿐이다**: 위키 정제 결함 전수 스캔(8절), FW2↔HPLT 중복 추정(6절), benchmark 겹침(9절), 비한국어 비중(10절), 스팸·도박 정규식 비율(3절). 이들은 모델 판단에 기대지 않는다.
- **스팸·SEO 비율(약 11%)은 방향성 근거로만 쓴다.** 두 라벨러의 건수가 같았고, JUN도 스팸 삽입 표시를 한 3건(D033, D037, D140)을 모두 제외했다. 그러나 3건은 확인 표본이 작고, 삽입 문서를 사용 가능으로 본 D013과 방향이 다르다. 구간(약 6~20%)은 모델 판정 기준이다.
- **정제 방침 (b):** 자동 필터는 모델 라벨러 없이 사전 기준만 쓴다 - 스팸·도박·출장마사지 키워드, 한국어 문자 비율, 길이 하한, 반복·중복 비율. 어떤 임계값도 JUN 판정 50건에 맞춰 튜닝하지 않으며, 적용 전후의 제거 비율만 보고한다. 문서 단위 "품질 점수"는 만들지 않는다.
- JUN 판정 50건은 폐기하지 않고 소표본 증거로 둔다. 상거래 안내·개인 블로그·짧은 설명글을 JUN이 사용 가능으로 본 경향은 필터가 너무 공격적이면 안 되는 이유로 쓰고, 스팸 삽입은 제외한다는 방향은 키워드 필터의 근거로 쓴다(13.3의 가설 수준).

요약: **"무엇을 어떻게 만들었는지 확인하기에는 매우 좋은 코퍼스, 그러나 권리와 품질 측면에서는 그대로 쓰기에 조심해야 하는 코퍼스."** 연구·재현 용도로는 가치가 크고, 상업적 재사용이나 한국어 모델 품질 입증에는 보강이 필요하다.

## 6. FineWeb2↔HPLT 교차 중복 측정 상세

**(1) exact 전수 검증 (A).** `splits/*.parquet`의 `content_sha256`(NFC SHA256, 공백·대소문자 보존)을 두 소스 전체에서 읽어 앞 8바이트로 대조.

| | 문서 수 | 소스 내 중복 | 소스 간 공통 해시 |
|---|---:|---:|---:|
| fineweb2_ko | 58,664,414 | 0 | **0** |
| hplt_ko | 27,434,232 | 0 | |

`data/dedup.py`가 소스 순서 기준 cross-source exact dedup을 하도록 설계돼 있으므로 정의대로 0건이다. 8,600만 건에서 8바이트 앞부분 충돌도 없었다.

**(2) 근접 중복 추정 (B).**

*검출기.* 공백 분리 어절 5-gram shingle, NFKC·소문자 정규화, 최대 5,000어절, 128 permutation MinHash, 32 band×4 row LSH, 후보는 128개 서명 일치율로 Jaccard(J) 추정. 300자 미만·5어절 미만 문서는 양쪽에서 제외. 검증: 어절 0%/2%/5%/10%/30% 변경 시 추정 J가 1.00/0.83/0.63/0.41/0.10, 무관 문서 0.00. 따라서 **J≥0.8은 어절 약 2~3% 이내만 다른 사실상 동일 글**, J≥0.5는 약 8% 이내 변경이다.

*1차 측정(설계 결함).* HPLT 5개 파일(286,821건)을 FineWeb2 파일 하나(전체의 4.6%)에 대조하니 파일 `000_00003`에서 J≥0.8 적중 1.93%, `003_00002`에서 0.57%로 3.4배 차이가 났다. 중복이 파일 단위로 군집돼 있어 파일 통째 인덱싱은 부적절했다.

*개선 설계.* FineWeb2는 25개 파일 전부에서 row group을 무작위 추출(654개, 약 251만 문서, 전체 행의 4.57%)하고 시드 3개(101, 202, 303)로 반복. HPLT 쿼리는 464개 파일 중 58개를 등간격(4, 12, …, 460번째)으로 추출(3,455,188문서, HPLT의 약 12.6%). 신뢰구간은 HPLT 파일 58개 간 적중률 편차(SE)에서 ±2SE로 계산했다. 환산은 "적중률 ÷ 인덱스 비율"이다.

| 시드 | J≥0.8 파일평균 적중률 | J≥0.8 전체 환산 [95% 구간] | J≥0.5 전체 환산 [95% 구간] |
|---|---:|---:|---:|
| 101 | 1.09% | 24.0% [19.4, 28.5] | 42.6% [35.4, 49.8] |
| 202 | 1.07% | 23.3% [18.9, 27.8] | 42.0% [34.9, 49.1] |
| 303 | 1.04% | 22.7% [18.4, 27.0] | 41.0% [34.1, 47.9] |
| **평균** | | **23.3%** (22.7–24.0) | **41.9%** (41.0–42.6) |

세 시드는 같은 쿼리를 쓰므로 평균해도 구간은 좁아지지 않는다. 구간은 HPLT 쿼리 쪽 변동이 지배한다. 가중 합산(pooled) 적중률은 0.95~1.00%.

*읽는 법과 한계.*
- **해석:** "HPLT 문서 중 FineWeb2에 사실상 같은 글(J≥0.8)이 있는 비율이 약 23%(구간 18~29%)"로 읽는다. 한 문서에 FineWeb2 쌍이 여럿이면 과대추정 방향이다(환산은 쌍 수의 기댓값에 가깝다).
- **J≥0.5(약 42%)** 는 어절 약 8% 변경까지 포함하므로 같은 글의 변형·부분 겹침이 섞인다. 사실상 동일 글의 하한으로는 J≥0.8을 쓴다.
- **쌍 내용:** 무작위 14쌍을 읽은 결과 오탐이 아닌 같은 글이었고 차이는 머리글·꼬리말·메뉴·공백 등 주변 텍스트였다. 한 쌍(J=0.95)은 시작 부분이 달라 본문 일부만 겹쳤다. J=1.00 쌍은 shingle 집합이 같지만 NFC 바이트가 달라 exact 해시를 통과했다.
- **군집:** HPLT 파일별 적중률은 최소 0.04~0.07%, 중앙값 약 1.4%, 최대 약 2.1%로 30배 편차가 있고, FineWeb2도 파일별 매치 수가 4~305건으로 고르지 않다(1차 측정 기준). 군집의 원인(크롤 시기·도메인 순서 등)은 미확인이다.
- **방향:** HPLT→FineWeb2만 측정했다. 일대일 대응을 가정하면 FineWeb2 쪽 비율은 약 11%(0.233×27.4M÷58.7M)이나, 이 환산은 가정에 의존한다.
- **토큰 환산(거친 곱셈):** HPLT 28.77B × 23% ≈ 6.6B 토큰, 한국어 웹 71.4B의 약 9%. 중복 문서의 길이 편향을 측정하지 않았으므로 문서 기준 비율을 그대로 곱한 값이다.
- **미측정:** FineWeb-Edu 등 다른 소스와의 중복, 300자 미만 문서, 전수 처리 결과.
- 측정 스크립트는 세션 작업 디렉터리에만 있고 저장소에 포함하지 않았다.

## 9. 한국어 benchmark 겹침(오염) 검사 상세 (B)

**방법.** 접근 가능한 공개 benchmark 7종의 test/validation 문항(KMMLU 45과목, HAE-RAE Bench 1.1, KoBEST 5과제, KLUE-MRC·NLI, KorMedMCQA, KorQuAD 1.0, HRM8K)을 정규화(NFKC·소문자·구두점 제거)한 어절 8-gram shingle로 색인(고유 3,110,423개, 15어절 이상 평가 가능 문항 53,939개)하고, 코퍼스 스캔 범위에서 한 문항의 shingle이 몇 %나 발견되는지(coverage)를 센다. 스캔 범위: Wikipedia 전량 455,397건, FineWeb2 row group 층화 4.57%(2,678,766건), HPLT 58개 파일 12.6%(3,455,442건). **해석.**
- **독해형(KorQuAD, KLUE-MRC, BoolQ):** 지문이 위키·뉴스 본문이라 코퍼스에 있는 것이 자연스럽다. Wikipedia 한 소스만으로 KorQuAD 지문의 80%가 찾아지고, 웹 표본(HPLT 12.6%)에서도 KorQuAD 지문 294건(30.6%)이 추가로 발견된다. 웹 전체를 보면 더 높을 것이다. BoolQ는 ≥0.5가 73%인데 ≥0.8은 28.7%로, 지문 일부가 위키 판본 차이로 부분 일치하는 경우가 많다.
- **KMMLU:** 9건을 문서에서 직접 열어 확인한 결과 8건은 문항 전체(앞 12어절과 뒤 12어절)가 문서에 있었고 1건은 앞부분만 있었다. 같은 문서에 여러 문항이 묶여 있어 시험 문제 모음 페이지가 원인으로 보인다. 스캔 비율(FW2 4.57%, HPLT 12.6%)로 단순 환산하면 FW2 전체에서 약 170건(포아송 95% 구간 약 77~346), HPLT 전체에서 약 8건 수준이며, 평가 가능 문항의 1% 미만으로 추정된다(불확실, 같은 문항이 양쪽에 있을 수 있음).
- **HAE-RAE, HRM8K, KorMedMCQA, KoBEST hellaswag/wic:** 80% 이상 겹침 0건.
- **판정 불가:** 15어절 미만 문항은 우연 일치와 구분이 안 돼 제외했다(KoBEST-SentiNeg 397문항 전부, KoBEST-COPA 1,000 중 941, KLUE-MRC 질문 5,841 중 5,822, KorQuAD 질문 5,764 중 5,577, KLUE-NLI 3,000 중 1,366 등). 따라서 **질문·정답 수준의 누출은 이 검사로 판정할 수 없다.**

**한계.** 어절 8-gram 정확 일치라서 번역·패러프레이즈는 못 잡는다. FineWeb2·HPLT는 일부만 스캔했다. 한 문서에서 일치한 것인지 여러 문서에 흩어져 일치한 것인지를 구분하지 않고 코퍼스 전체 합집합으로 coverage를 계산했다(독립 검증은 KMMLU 9건만 수행).

## 12. JUN 정답 세트와 모델 라벨러의 대조 (27건)

JUN이 D001~D030 중 27건을 판정했다(D016, D018, D019 미입력). 판정 3분류만 사용했고 장르·태그·메모는 비어 있다. 따라서 장르 규칙(E6)은 이번에 검증되지 않았다. 정답 파일은 12.1절 갱신 이후 `docs/labeling/labels_jun_gold.json`(30건, 본문 없음)이다.

| 비교 | 4분류 일치 (kappa) | 사용 가능/제외/판단 불가 3분류 (kappa) | 둘 다 판정한 문서에서 사용 가능 vs 제외 |
|---|---:|---:|---:|
| JUN vs Claude | 55.6% (0.33) | 77.8% (0.39) | 80.8%, n=26 (0.44) |
| JUN vs 서브에이전트 | 40.7% (0.16) | 66.7% (0.26) | 75.0%, n=24 (0.36) |
| (참고) Claude vs 서브에이전트, 150건 전체 | 84.7% (0.78) | 87.3% (0.73) | 96.2%, n=132 (0.91) |

사전 등록한 기준(정답 세트에서 kappa 0.6 이상)을 충족하지 못했다. **두 모델은 서로 비슷하게 판정하지만 JUN과는 체계적으로 다르다.** 모델 둘이 같은 방향으로 틀릴 수 있다는 뜻이다.

**사용 가능 비율 (27건).** JUN 23건(85%), Claude 19건(70%)+판단 불가 1, 서브에이전트 16건(59%)+판단 불가 3. 모델이 JUN보다 엄격하다. JUN이 제외한 4건(D002 위키 토막글, D007 기계번역 뉴스, D013 시험 덤프 스팸, D029 커뮤니티 글) 중 Claude는 3건, 서브에이전트도 3건을 제외로 판정했다. 모델이 제외했지만 JUN은 사용 가능으로 본 문서가 Claude 기준 7건 중 4건, 서브에이전트 기준 8건 중 5건이다.

**갈린 문서와 유형 (JUN / Claude / 서브에이전트).**

| 유형 | 문서 | 판정 |
|---|---|---|
| 기계번역 문체 (E4) | D001 번역투 심리학 글 | 정제 / 제외 / 제외 |
| | D011 번역투 공연 안내문 | 정제 / 제외 / 제외 |
| 레포트 판매 페이지 (잡음 약 54~55%로 추정) | D006 | 정제 / 제외 / 제외 |
| | D020 | 그대로 / 제외 / 제외 |
| 위키 토막글 | D002 (219자) | 제외 / 정제 / 정제 |
| | D012 (281자) | 그대로 / 정제 / 제외 |
| 경계 구간(8~12%)에서 모델이 판단 불가 | D009, D010, D015, D023 | JUN은 모두 사용 가능 (그대로 3, 정제 1) |
| 그대로 사용 vs 정제 후 사용 | D004, D014, D021, D022, D027 | JUN은 정제 / 모델은 그대로 사용 |

- **기계번역 문체는 일관된 규칙이 아니다.** JUN은 D001, D011은 사용 가능으로 보고 D007(문장이 깨진 기계번역 뉴스)은 제외했다. 읽어서 정보를 얻을 수 있는지가 기준일 가능성이 있으나 추정이다.
- **JUN은 "판단 불가"를 쓰지 않았다.** 모델이 경계라며 보류한 4건을 JUN은 모두 사용 가능으로 판정했다. 경계 구간 판단 불가는 사용 가능으로 계산하는 것이 맞다.
- **그대로/정제 구분은 JUN이 더 보수적**(기자·저작권 줄이 있으면 정제)이었으나, D020은 잡음이 모델 추정으로 54%인데도 "그대로"였다. 이 구분은 JUN 본인에게서도 일관되지 않을 수 있다(재검증은 하지 않음).
- 문서 수가 27건이고 JUN의 반복 일관성은 측정하지 않았다. 위 패턴은 가설이다.

**민감도 시나리오: 판정 기준에 따른 웹 소스 사용 가능 비율.** 아래는 정답 세트에서 관측한 조건부 비율을 표본 크기가 작은 채로 그대로 적용한 계산이며 추정값이 아니다(Claude 제외 7건 중 JUN 제외 3건, Claude 사용 가능 19건 중 JUN 제외 1건).

| 기준 | 웹(fineweb2+hplt) 무작위 80건 |
|---|---:|
| 모델 라벨러 기준 | 약 65~70% |
| JUN 기준으로 보정하면 | 약 80~85% (표본이 작아 구간이 매우 넓음) |

따라서 11절의 사용 가능 비율은 정책에 따라 15%p 정도 움직일 수 있다. 차이의 대부분은 모델의 판정 능력이 아니라 **기계번역 문체와 레포트 판매 페이지를 사용 가능으로 볼지**라는 기준 문제다.

**다음 단계 (기준 v3 후보).** 사용 가능/제외를 1차 지표로 삼고 그대로/정제 구분은 보조 정보로 낮춘다. 경계 구간 판단 불가를 없앤다. E4는 "정보 추출이 불가능할 정도로 깨진 경우"로 한정한다. 레포트 판매 페이지와 위키 토막글 기준은 JUN의 답을 받아 정한다. v3로 150건 중 정답 세트 밖 120건을 다시 라벨링해 비교한다.

### 12.1 30건 재확인 (D016, D018, D019 입력 후)

JUN이 12절의 대조 결과를 본 뒤 여러 문서를 다시 열었고, 30건이 모두 채워졌다. 최초 판정 이후 **판정이 바뀐 문서는 3건**이다(D003 그대로→제외, D006 정제→제외, D013 제외→정제). 나머지 판정은 유지됐으므로 JUN이 모델 판정을 따라간 것은 아니다. 다만 수정 시점이 비교 결과를 본 이후라서 정답 세트가 모델과 완전히 독립이라고는 할 수 없다. 장르는 20건, 태그는 11건, 메모는 0건이 입력됐다.

| 비교 (30건) | 4분류 일치 (kappa) | 둘 다 판정한 문서에서 사용 가능 vs 제외 | 판단 불가를 사용 가능으로 계산 (n=30) |
|---|---:|---:|---:|
| 최초 판정 vs Claude | 53.3% (0.29) | 82.1%, n=28 (0.44) | 83.3% (0.45) |
| 최초 판정 vs 서브에이전트 | 40.0% (0.14) | 76.9%, n=26 (0.37) | 80.0% (0.39) |
| 현재 판정 vs Claude | 50.0% (0.25) | 78.6%, n=28 (0.37) | 80.0% (0.38) |
| 현재 판정 vs 서브에이전트 | 36.7% (0.10) | 73.1%, n=26 (0.30) | 76.7% (0.32) |

- 어느 경우에도 사전 등록 기준(kappa 0.6)에 못 미친다. 수정으로 일치도가 약간 낮아졌다(D003, D013이 모델과 반대 방향으로 바뀌었기 때문).
- 사용 가능 비율: JUN 25/30(83%), Claude 21/30(70%)+판단 불가 2, 서브에이전트 18/30(60%)+판단 불가 4.
- **입력 오류가 의심되는 판정.** D003(중앙일보 코로나 격리 칼럼)을 JUN이 "제외"+태그 "외설·유해"로, D013(시험 덤프 스팸)을 "정제 후 사용"+태그 "기타"로 바꿨다. 둘 다 최초 판정이나 모델 둘과 반대이고 근거(메모)가 없다. 버튼 오입력일 가능성이 있어 JUN에게 확인을 요청했다. JUN이 두 건 모두 의도한 판정임을 확인했고(2026-11-09), 정답 세트에 그대로 사용한다.
- 새로 입력된 3건: D016은 모두 "그대로 사용", D018은 JUN "그대로 사용"·모델 "정제 후 사용", D019는 JUN "그대로 사용"·모델 "판단 불가(경계)". 사용 가능 방향은 모두 일치했다.
- 갈림 유형은 12절과 같다: 기계번역 문체(D001, D011), 레포트 판매 페이지(D020), 위키 토막글(D002, D012), 경계 구간 판단 불가(D009, D010, D015, D019, D023). JUN이 D002에 단 태그는 "낮은 정보량"이라 토막글은 길이보다 담긴 정보량 기준으로 판단했을 가능성이 있다(추정).
- **장르.** 입력된 20건 중 모델과 일치 13건(65%). 갈린 7건은 대부분 인접 범주다(블로그 vs 커뮤니티 D029, 블로그 vs 뉴스 D007, 설명글 vs 뉴스 D017, 설명글 vs 상거래 D011·D013 등). 장르 규칙(E6)은 입력이 불완전해 검증하지 못했다.
- **태그.** JUN의 태그는 모델 태그와 거의 겹치지 않았다(JUN은 "형식 깨짐"을 기사 4건에 사용, 모델은 같은 문서에 "보일러플레이트·메뉴"). 태그 어휘의 해석이 달라 태그 단위 비교는 의미가 작다.

**결론.** 사용 가능 vs 제외 판정에서 모델은 JUN보다 엄격하고(제외 7~8건 vs JUN 5건), 갈리는 원인은 모델의 판정 능력보다 기준(기계번역 문체, 레포트 판매 페이지, 토막글 정보량의 허용 폭)이다. 정답 세트가 30건이고 일부가 의심 입력이라, 11절의 사용 가능 비율은 "모델 기준 65~70%, JUN 기준으로 보정하면 80% 안팎"이라는 범위로만 읽어야 한다.

## 13. 기준 v3 검증: 정답 세트 밖 20건 (결과: 기준 미달)

절차는 `docs/labeling/RUBRIC_v3.md`에 사전 등록한 대로 진행했다. D031~D150 120건을 Claude와 독립 하위 에이전트가 v3로 블라인드 라벨링했고(`labels_claude_v3.json`, `labels_agent_v3.json`), 그중 20건을 뽑아 JUN이 모델 판정을 보지 않고 판정했다(`labels_jun_v3_validation.json`, 선정 `validation_set_v3.json`, 시드 20261109). 20건은 불일치 8건(전체 15건 중), 둘 다 제외 5건(15건 중), 둘 다 사용 가능 7건(90건 중)이다. 불일치를 과대표집했으므로 모집단 비율로 가중해 계산했다.

### 13.1 모델 간 일치 (120건)

| | 사용 가능 | 제외 |
|---|---|---|
| Claude v3 | 103 | 17 |
| 하위 에이전트 v3 | 92 | 28 |

일치 105/120, kappa 0.595. Claude는 68건을 v2 사용 가능 판정에서 승계했고 하위 에이전트는 전체를 새로 봤으므로, 이 값은 두 라벨러가 대칭이 아닌 상태의 수치다(승계가 일치도를 낮춘 방향인지는 확인하지 못했다).

### 13.2 JUN과의 일치 (20건, 사용 가능 vs 제외)

| 대조 | 단순 일치 | kappa(비가중) | kappa(모집단 가중) | 부트스트랩 95% 구간(가중) |
|---|---|---|---|---|
| JUN vs Claude | 13/20 | 0.20 | 0.28 | -0.09 ~ 0.75 |
| JUN vs 하위 에이전트 | 13/20 | 0.33 | 0.35 | -0.06 ~ 0.79 |

**기준 0.6에 도달하지 못했다.** 구간이 매우 넓어(표본 20건) "0.6 이상일 가능성"을 완전히 배제하지는 못하지만, 점추정은 v2(0.25~0.38)와 사실상 차이가 없다. v3 규칙이 JUN의 판단을 재현한다는 근거는 얻지 못했다.

### 13.3 어긋난 7건에서 읽히는 것 (추정, 표본 7건)

- **JUN은 상거래·안내 페이지를 사용 가능으로 본다**: D065(배송·결제 안내), D124(판매자 정보·반품 안내)를 사용 가능으로 판정했다. 둘 다 v3 규칙 A(약관·결제 안내는 본문이 아님)로는 본문이 남지 않아 제외가 되는 문서다. 앞서 D020(레포트 판매 페이지)도 같은 방향이었다. 모델 둘은 두 문서를 모두 제외했다.
- **JUN은 개인 블로그·후기를 사용 가능으로 본다**: D072, D080을 사용 가능으로 판정했다. Claude는 제외했다(하위 에이전트는 사용 가능).
- **JUN은 짧은 설명·소개글에 관대하다**: D081(인물 설명), D085(옷 설명), D145(웹소설 소개 목록), D045(뉴스 모음 요약)를 사용 가능으로 판정했다. 하위 에이전트는 넷 모두 제외했다.
- **JUN은 스팸 삽입 문서를 제외한다**: 스팸 삽입 표시를 한 3건(D033, D037, D140)을 모두 제외했다. v3는 삽입을 제거한 뒤 남는 본문으로 판단하므로 D033, D140을 사용 가능으로 봤던 Claude와 어긋난다. D013(삽입 문서를 사용 가능으로 판정)과는 방향이 다르다. D013 판정과 이번 3건을 하나의 규칙으로 묶으려면 삽입 비율이나 삽입의 성격 같은 추가 기준이 필요한데, 현재 데이터로는 정할 수 없다.
- 요약하면 JUN의 기준은 "정보량·번역·잡음 비율"보다 "사람이 쓴 자연스러운 한국어 글인가, 스팸·불법·무의미한 글인가"에 가깝다는 가설이 가장 잘 맞는다. 다만 표본이 작고 이 가설은 이번 20건과 앞선 30건을 보고 세운 것이라, 새 문서로 다시 검증하기 전에는 규칙으로 쓰지 않는다.

### 13.4 사용 가능 비율 보고

- 모델 기준(120건): Claude 103건(86%), 하위 에이전트 92건(77%). 사용 가능 중 그대로 사용 / 정제 후 사용 / 삽입 제거 필요는 Claude 54/42/7, 하위 에이전트 57/29/6.
- JUN 기준(20건): 사용 가능 14건. 모집단 가중 추정은 약 79%(94/120)이나 표본 20건이라 구간이 넓다(대략 ±20%p 이상으로 읽을 것, 구간은 계산하지 않았다).
- 따라서 "FW2·HPLT 웹 문서의 사용 가능 비율은 약 80% 안팎"이라는 이전 문장은 유지하되, 모델 라벨러로는 JUN 판단을 신뢰성 있게 재현하지 못한다는 점이 확정됐다. 이 비율의 의미는 "JUN이 쓸 만하다고 본 문서의 비율 추정"이지 "모델 라벨러가 측정한 값"이 아니다.
- 스팸 삽입 문서를 사용 가능으로 세는 것은 삽입 문장 제거기가 있다는 가정에 의존한다. JUN이 삽입 문서 3건을 모두 제외했으므로, 삽입 제거기가 없다면 사용 가능 비율은 위 수치보다 낮아진다.

### 13.5 결론과 다음 선택지

- 모델 라벨러를 JUN 판단의 대리로 쓰는 것은 현재 근거로는 불가능하다. 규칙 개정(v2→v3)은 두 번 모두 kappa를 올리지 못했다.
- 이 20건으로 v3를 다시 고치면 새 검증 세트가 필요하다(이 20건은 이미 규칙에 반영될 수 있는 정보가 됨).
- 선택지는 (a) JUN이 직접 라벨링한 건수를 늘려 JUN 판정을 학습 데이터로 쓰는 분류기를 만들거나, (b) 모델 라벨러를 품질 비율 측정에 쓰지 않고, 단순한 사전 기준(스팸·도박 키워드, 한국어 비율, 길이)만 자동 필터로 쓰는 것이다. JUN 판정 50건은 폐기하지 않고 소표본 증거로 둔다(5.1절). 어느 쪽이든 현재 데이터로는 "품질 비율"을 좁은 구간으로 말할 수 없다.
- **결정: (b)로 진행한다.** 모델 라벨러는 품질 비율 측정에 쓰지 않는다. 5.1 참조.
